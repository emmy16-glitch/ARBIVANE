# Stage 32 — resumable current-Pyth sweep of every verified Rhea debt finding

A **complete real NEAR mainnet scan** at finalized block `221436207` found **72,782 accounts, 7,801 debt accounts and 7,801 debt positions** with four zero-error shards. Source: successful workflow run `40128285853`. Stage 31 revalidated the initial 12: 6 reference-healthy, 6 blocked and no paper-at-risk (as of that observation). None of those 7,801 debt findings represents a verified live liquidation opportunity.

Stage 32 consumes the **fully verified** Stage30 artifact, runs the existing current-price active Pyth Stage31 model over larger slices of the 7,801 debt findings and checkpoints after each 20-account batch. `full-active-pyth-sweep.ts` enforces strict source identity, account order and coverage, exact cursor continuation, mutually consistent status counts, non-authorizing safety flags and deterministic rejection of forged/resumed findings. Individual RPC failures retain `BLOCKED_RPC`; they never count as health-positive or liquidation-eligible.

GitHub Actions workflow `rhea-stage32-resumable-pyth-sweep.yml` automatically starts after its merge to main. It assigns four **nonoverlapping slices of 80 debt findings each** with two workers maximum simultaneously, preventing overload of the public read-only RPC. The default first run starts at debt finding `12` (after Stage31 initial batch), covering indices `[12,332)`. For the next 320, manually dispatch with `base_cursor=332` using verified source scan run `40128285853`. Repeat with sequential values 652, 972, etc.; the final window may have fewer than 320. This is a bounded progressive sweep, **not a claim that all 7,801 were repriced automatically in the first run**.

For a failed run, pass its `resume_run_id` alongside the same `base_cursor` and source scan ID. The workflow downloads the previous shard-specific checkpoint artifacts, validates the source block, code hash, starting indices and every saved borrower record, then continues without discarding completed batches. If no valid checkpoint exists, it fails rather than pretending a full run occurred. A failed public RPC should not trigger uncontrolled repeated retries.

Each shard artifact carries `stage32-reprice-checkpoint.json`, `stage32-reprice-report.json` and `stage32-summary.json`, with explicit counts for blocked, paper-at-risk, paper-healthy and no-longer-debted accounts. Every borrower recheck obtains fresh on-chain data; separate accounts are not guaranteed to share a finalized block. Stage32 **does not** establish any liquidation contract parity, stateful Sandbox replay, financing, borrow cap, gas, swap, competition visibility, or realized profit. `executionEnabled=false`, `maySign=false` and `mayBroadcast=false` are invariant.

For genuine money execution, subsequent stages must verify the deployed liquidation rules and full-fidelity stateful transaction outcome, use exact atomic amounts and economic constraints, then secure explicit owner spending authorization. No PDF, signer or private key is used in this stage.
